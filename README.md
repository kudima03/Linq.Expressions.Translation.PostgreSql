# Linq.Expressions.Translation.PostgreSql

Translates the expression tree of an `IQueryable<T>` into a single PostgreSQL `SELECT` statement.

## What is translated

- `Where`, `Select`, `OrderBy`/`OrderByDescending`/`ThenBy`/`ThenByDescending`, `Order`/`OrderDescending`, `Skip`, `Take`, `TakeLast`, `SkipLast`, `Distinct`, `DistinctBy`, `Reverse`, `Cast` and `OfType`; an operator that cannot extend the current `SELECT` (for example `Where` after `Take`) wraps it into a derived table, which exposes ordering keys the projection hides as extra `"$n"` columns so that the order survives (also for `Reverse`, `Last` and `TakeLast`). A later `OrderBy` sorts stably, as in LINQ to Objects: the keys of an earlier ordering follow its keys and those of its `ThenBy`. The ordering operators accept `StringComparer.Ordinal` (`ORDER BY ... COLLATE "C"`, the byte-wise order of UTF-8, which is code-point order). `DistinctBy` is `SELECT DISTINCT ON (keys)`, whose `ORDER BY` has to start with the keys: a source order that does not (`OrderByDescending(o => o.PlacedAt).DistinctBy(o => o.UserId)`, the latest order per user) is restored outside a derived table, into which every later operator other than a projection or paging also wraps the kept rows. `Distinct` yields the first occurrence of each value in the order of the source, as in LINQ to Objects: `SELECT DISTINCT` ordered by the selected values where they are ordered by themselves (`OrderBy(c => c.Region).Select(c => c.Region).Distinct()`), otherwise `DISTINCT ON` the values in the order of the source, restored outside as for `DistinctBy` (`OrderByDescending(c => c.Id).Select(c => c.Region).Distinct()` is `SELECT t1."Region" FROM (SELECT DISTINCT ON (t0."Region") t0."Region", t0."Id" AS "$0" FROM "Customer" AS t0 ORDER BY t0."Region", t0."Id" DESC) AS t1 ORDER BY t1."$0" DESC`).
- Comparison, logical, arithmetic, bitwise and conditional operators, `??`, conversions (a `DateTime` compares with a `DateTimeOffset` through PostgreSQL's session time zone; a `DateTime` constant is a `TIMESTAMP` whatever its kind, as C# compares `DateTime` values by their ticks, and a `Utc` one converted to a `DateTimeOffset` keeps its zero offset), string concatenation, `Nullable<T>` members and constructed objects (`new Summary(c.Id, c.Name)`, also of constants only), which are projected member by member, as is a constant tuple (`default(ValueTuple<int?, string?>)` or a captured one, whose members become literals, `NULL` for a default). `string.CompareOrdinal(a, b)` compared with `0` is `a COLLATE "C" < b` (`<=`, `>`, `>=`, `=`, `<>`), ranking a null operand below every string as .NET does (`a IS NULL OR a COLLATE "C" < b`).
- `string` members (`Length`, case conversion, trimming (`Trim()` removes every .NET white-space character, not only spaces), `Substring`, `Remove`, `IndexOf`/`LastIndexOf`/`IndexOfAny`, `Replace`, `Contains`/`StartsWith`/`EndsWith` as `LIKE` with escaped wildcards, `IsNullOrEmpty`, `Concat`, `Format` and interpolated strings without alignment or format strings; lengths and positions count code points, as PostgreSQL does, not UTF-16 code units, so a character outside the Basic Multilingual Plane, an emoji for example, counts once instead of twice), `Math` functions (`Round` half to even, .NET's default, or away from zero, of decimals and doubles, also to digits) and their `int`/`long`/`decimal`/`double` counterparts, `double.IsNaN`/`IsInfinity`/`IsFinite`, date and time parts and arithmetic (`DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly`), `TimeSpan` fields and totals (`Days`, `Hours`, ..., `TotalDays`, ..., `Ticks`), `DateTime.Now`/`UtcNow`/`Today`, `DateTimeOffset.Now`/`UtcNow`, `Guid.NewGuid`, `Enum.HasFlag` and `ToString` of numbers and `Guid`. `Encoding.UTF8.GetString(bytes)` reads a `byte[]` (`bytea`) as text, `CONVERT_FROM(..., 'UTF8') COLLATE "default"` (the collation of the database, as a text column has it; `convert_from` alone yields the `"C"` collation of the encoding's name, under which `UPPER` and `LOWER` map ASCII letters only), over which the text operations compose, and `Encoding.UTF8.GetBytes(text)` is `CONVERT_TO(..., 'UTF8')`; PostgreSQL fails on bytes that are no UTF-8 where .NET replaces them, other encodings and the partial overloads are rejected, and a `byte[]` constant is a `BYTEA '\x...'` literal. Ticks are 100 ns since `0001-01-01`: `DateTime.Ticks` and `TimeOnly.Ticks` come from `EXTRACT(EPOCH FROM ...)`, and `TimeSpan.FromTicks`, `AddTicks` and `new DateTime(ticks[, kind])` of a computed count become interval arithmetic in microseconds (PostgreSQL keeps no finer unit; the kind has to be a constant other than `Local`, and `Utc` adds `AT TIME ZONE 'UTC'`). `Parse` of `bool` and `Guid`, and of numbers and `TimeOnly` with `CultureInfo.InvariantCulture` (plus a constant `NumberStyles`/`DateTimeStyles`), is `CAST(... AS boolean | uuid | bigint | numeric | ... | time)`: the text has to be in PostgreSQL's input syntax, which also accepts forms .NET rejects; the current-culture overloads are rejected, and so is a `NumberStyles` the cast cannot honour, one with `AllowHexSpecifier` or `AllowBinarySpecifier`, which would read another number, or one without the sign and the white space of `NumberStyles.Integer`, which the cast accepts whatever the style. `DateOnly.Parse` and `DateTime.Parse` with the invariant culture are `TO_DATE(..., 'MM/DD/YYYY')` and `TO_TIMESTAMP('+00 ' || ..., 'TZH MM/DD/YYYY HH24:MI:SS') AT TIME ZONE 'UTC'`, which read the invariant short date month first whatever the server's `DateStyle`, at the same cost as a cast: a month and a day of one or two digits, a four-digit year, any single separator (`1/2/2024`, `01-02-2024 10:30:00`, also with `.`), leading spaces and a 24-hour time that may be missing or lack its seconds; fractional seconds, an AM/PM marker and anything else after the seconds are dropped, a two-digit year is the year itself (`1/2/24` is the year 24), and any other form, ISO 8601 or a month name for example, fails on the server. The fixed `+00` offset, taken back as UTC, keeps a `DateTime` as written even in a daylight-saving gap of the session's time zone. With `DateTimeStyles.AssumeUniversal | DateTimeStyles.AdjustToUniversal` the `TO_TIMESTAMP(...)` stays a `timestamptz`, the instant the text says in UTC, which Npgsql reads with the kind `Utc`; `AssumeUniversal` alone and `AssumeLocal`, which convert through or read in the local time zone of the client, are rejected, as the server does not know it.
- Dates and times built from parts: `new DateOnly(year, month, day)` is `MAKE_DATE(...)`, `new TimeOnly(hour, minute[, second[, millisecond[, microsecond]]])` is `MAKE_TIME(...)` with the seconds and their fraction added up exactly in `numeric`, `new TimeOnly(ticks)` is midnight plus the microseconds of the ticks, `new DateTime(year, month, day[, hour, minute, second[, millisecond[, microsecond]]][, kind])` is `MAKE_TIMESTAMP(...)`, `new DateTime(date, time[, kind])` and `DateOnly.ToDateTime(time[, kind])` are the date plus the time, and `DateOnly.FromDayNumber(n)` counts days from `0001-01-01`; a constant kind of `Utc` adds `AT TIME ZONE 'UTC'` as for ticks. They fail on the server where .NET throws: `MAKE_DATE`, `MAKE_TIME` and `MAKE_TIMESTAMP` reject an invalid month, day or minute themselves, and a year outside 1..9999, an hour of 24, a second of 60, a millisecond or microsecond above 999, ticks of a day or more and a day number past `9999-12-31` turn the year into 0 or the hour into -1, which they reject (`MAKE_DATE(CASE WHEN (t0."Year" >= 1) AND (t0."Year" <= 9999) THEN t0."Year" ELSE 0 END, ...)`; a constant part in range needs no guard). The `Calendar` overloads and the kind `Local` are rejected. `AddMonths` and `AddYears` keep the day, or the last day of a shorter month, as .NET does (`2024-01-31` plus a month is `2024-02-29`); past `9999-12-31` PostgreSQL keeps counting where .NET throws.
- `Contains` (and `Any(x => x == value)`) on in-memory collections (`IN (...)`) and on array columns (`= ANY (...)`, which is `COALESCE(..., FALSE)` as a value or under `NOT`, as an array may hold `NULL` elements), plus array `Length`, `Count()` and `Any()`.
- Terminal operators: `Count`/`LongCount`, `Sum`, `Average`, `Min`, `Max` (of booleans as `BOOL_AND`/`BOOL_OR`; `Min`/`Max` of `Guid` is rejected, as PostgreSQL orders uuids differently), `MinBy`/`MaxBy` (the first row in the order of the key, `NULLS LAST` so that elements with a null key are skipped unless every key is null, and then of the source, so that ties resolve as in .NET; `StringComparer.Ordinal` gives `COLLATE "C"`, and a `Guid` key is rejected like `Min`/`Max` of `Guid`), `Any`, `All`, `Contains`, `First`/`Single`/`Last`/`ElementAt` (and their `OrDefault` forms, which substitute the default of a value type inside a lambda), and aggregates after `DefaultIfEmpty()`.
- The same operators inside lambdas, as correlated or uncorrelated subqueries (`EXISTS`, `IN (SELECT ...)`, scalar subqueries). An aggregate (`Count`, `Sum`, `Average`, `Min`, `Max`, `Any`, `All`) in the projection of a query over the rows that projection reads — the same query, in any order, below any `Where` and `Select` of the aggregate's own — is a window aggregate over all of them, computed in the pass that reads the rows: `orders.Select(o => new { o.Id, Share = o.Total / orders.Sum(x => x.Total) })` is `SELECT t0."Id", t0."Total" / COALESCE(SUM(t0."Total") OVER (), 0) AS "Share" FROM "Order" AS t0`, and a filtered one is `COUNT(*) FILTER (WHERE ...) OVER ()`. The rows have to be the rows the projection reads (not once they are paged or made distinct) and the aggregate's lambdas must read nothing but their own element, otherwise it stays a scalar subquery; a filter, grouping, join or aggregate over a projection holding a window wraps it into a derived table, as SQL allows a window only in a projection, an order, paging or `DISTINCT`.
- `Join` (`INNER JOIN`; keys compare with `=`, so null keys never match, as in C#, while the members of a composite key, an anonymous type or a tuple that compares its members with the default comparer, match with `IS NOT DISTINCT FROM` when both are nullable), `GroupJoin` (aggregated groups as correlated subqueries, also after `Where`, `Select`, `OrderBy`, `Distinct` or paging of the group, or `LEFT JOIN` with `SelectMany`/`DefaultIfEmpty`, where a `Where` on the group before `DefaultIfEmpty()`, possibly chained, becomes part of the `ON` condition instead of dropping the unmatched rows) and `SelectMany` (`CROSS JOIN`, correlated `INNER`/`LEFT JOIN`, or a derived table when the inner source is paged, `JOIN LATERAL` if it also reads the outer element). A left-joined source that projects anything other than its own columns (a computed value, a constant, a column of the outer element) is joined as a derived table, so that an unmatched row reads it as `NULL`, as the default element is in LINQ to Objects, instead of evaluating it on the `NULL`s of the missing row. An outer row without a match reads the element `DefaultIfEmpty()` yields: `null` for a reference type (such a projection compared with `null` tests a column that is never `NULL` in a match, or every column when there is none, as a left-joined entity does), the default of a value type member by member (`COALESCE(..., 0)`, down to a reference or nullable member, which stays `NULL`), or the explicit default of `DefaultIfEmpty(value)`, which is translated only for a single value that is never `NULL` in a match, as `NULL` cannot be told from the absence of a row.
- `GroupBy` (with element and result selectors): `GROUP BY` the flattened key, `HAVING` for filters on groups, and aggregates over the group — `Count` (also with a predicate, as `FILTER (WHERE ...)`), `Sum`, `Average`, `Min`, `Max`, `Any`/`All` (`BOOL_OR`/`BOOL_AND`), `Where(...)` (possibly chained) before an aggregate and `Select(...).Distinct()` before `Count`, `Sum` or `Average` (`COUNT(DISTINCT ...)`, `SUM(DISTINCT ...)`, `AVG(DISTINCT ...)`; `Select` after `Distinct` is rejected, as the aggregate would apply to the distinct projected values). Over an ordered source the groups come in the order of the first element of each, as in LINQ to Objects: `ORDER BY` the key itself when it is a grouping key, `MIN`/`MAX` of a first ordering key that is never `NULL`, and otherwise the key of the group's first element in the order, `(ARRAY_AGG(key ORDER BY ...))[1]`.
- `Concat`, `Union`, `Intersect` and `Except` as `UNION ALL`, `UNION`, `INTERSECT` and `EXCEPT`, parenthesizing operands that are paged or a different set operation. `Concat` of an ordered side yields the first sequence in its order and then the second in its, as in LINQ to Objects: the sides are combined under a hidden `"$side"` column and the ordering keys of each, exposed as hidden columns that are `NULL` on the other side, and read from a derived table ordered by the side and then the keys; `Union`, `Intersect` and `Except` yield no order. `UnionBy` is `SELECT DISTINCT ON (keys)` over both sides combined with `UNION ALL`, each marked with a hidden `"$side"` column, ordered by the keys and then the side, so that the element of the first sequence is the one kept, as in .NET; the result has no order, like `Union`. `IntersectBy` and `ExceptBy` filter the elements on the membership of their key in the second sequence, a subquery (`IN (SELECT ...)`) or an in-memory collection of keys (`IN (...)`), with the null semantics of `Contains` (a null key matches a `NULL` of the sequence), and keep one element per key with `DISTINCT ON`, as `DistinctBy` does.
- Captured variables and parameter-free subtrees, which are evaluated in memory and rendered as literals. A subtree that throws when it is evaluated where it may not be reached (a branch of a conditional, the right operand of `??`, `&&` or `||`) is left to the database with the constants below it folded: `o.Id < 0 ? one / zero : o.Total` with `zero == 0` is `CASE WHEN t0."Id" < 0 THEN (SELECT 1) / 0 ELSE t0."Total" END`, where the scalar subquery keeps the planner from computing the division while it plans the statement, as PostgreSQL folds an operation on constants alone before any row reaches it. Elsewhere the exception propagates from the translation.
- One row of aggregates over tables: a constant one-element sequence as the root (`new[] { 0 }.AsQueryable().Select(_ => new { Orders = orders.Count(), Revenue = orders.Sum(o => o.Total) })`) is a `SELECT` of scalar subqueries without `FROM`. The element itself has no column and cannot be read. Joined on either side (`SelectMany`, `Join`, `GroupJoin`), the row is a derived table, which puts the totals next to every row: `customers.SelectMany(c => totals, (c, t) => new { c.Name, t.Orders })` is `FROM "Customer" AS t0 CROSS JOIN (SELECT (...) AS "Orders") AS t2`.
- In-memory sequences of scalars or of tuples of scalars (`ValueTuple` or `Tuple`, nested or of more than seven members) as a source: a root of two or more elements, the inner sequence of `Join`, `GroupJoin` or `SelectMany`, the second sequence of `Concat`, `Union`, `Intersect` or `Except`, or a subquery over one (`new[] { 1, 2 }.AsQueryable().Any(i => i == c.Id)`), are a `VALUES` list with a row per element, its columns named as a derived table's (`Value` for a scalar, `Item1`, ..., `Rest.Item1` for a tuple): `customers.Join(labels, c => c.Id, l => l.Id, (c, l) => new { c.Name, l.Label })` with `labels` an array of `(int Id, string? Label)` is `SELECT t0."Name", t1."Item2" AS "Label" FROM "Customer" AS t0 INNER JOIN (VALUES (1, CAST('one' AS text)), (2, NULL)) AS t1 ("Item1", "Item2") ON t0."Id" = t1."Item1"`. The first row writes the type of every column whose literal does not (`bigint`, `numeric`, `double precision`, `text`, a `NULL`), so that a `long` is not summed as an `integer`, a whole `decimal` is not divided as one and a column of `NULL`s compares with any column of its type; a column holding no `NULL` is not nullable. `SelectMany` from the one-element root to an in-memory sequence it does not read (`new[] { 0 }.AsQueryable().SelectMany(_ => rows, (_, row) => row)`) is that sequence. An empty sequence, a null tuple and an element of any other type (an entity, an anonymous type, a `char`, an array) are rejected, and so is a sequence computed from the outer element of `SelectMany` (`c => new[] { c.Id, c.Id + 1 }`).

- PostgreSQL features LINQ has no operator for, through the marker methods of [the PostgreSQL markers](#postgresql-markers): window functions over `OVER (PARTITION BY ... ORDER BY ... frame)` (`PostgreSqlWindows`, `PostgreSqlFrame`), `WITH RECURSIVE` with an optional depth limit that fails instead of cutting off (`PostgreSqlRecursion`).

Anything else — user-defined methods, culture- or comparison-specific overloads, navigation properties, in-memory sources other than those above, operators such as `Zip`, `Aggregate` or `SkipWhile` — throws `NotSupportedException` naming the offending member, method or expression node.

## Overview

The package exposes one public type that translates, `PostgreSqlQuery`, and the [PostgreSQL markers](#postgresql-markers), which only mark PostgreSQL's SQL in a tree. `PostgreSqlQuery` accepts a `System.Linq.Expressions.Expression` — the `Expression` of an `IQueryable<T>` — and exposes the PostgreSQL `SELECT` statement for that tree as its `TextValue`.

```csharp
IQueryable<Order> orders = ...; // any IQueryable<T> whose provider builds the tree

string sql = new PostgreSqlQuery(
    orders.Where(o => o.Total > 100).Select(o => o.Id).Expression
).TextValue;

// SELECT t0."Id" FROM "Order" AS t0 WHERE t0."Total" > 100
```

The package does not execute queries, open connections or materialize results; it only produces SQL text.

## PostgreSQL markers

PostgreSQL features that LINQ cannot express are written with marker methods, as `EF.Functions` is: they are named after PostgreSQL, follow PostgreSQL's semantics, exist only in expression trees (a lambda, or `Expression.Call` for a query operator outside one) and throw `NotSupportedException` when they are called, so that a provider that evaluates closed subtrees keeps the call in the tree.

| Type | Members | PostgreSQL |
|---|---|---|
| `PostgreSqlWindows` | `Over(source, partitionBy, orderBy, frame, (row, window) => ...)` | `SELECT ..., f(...) OVER (PARTITION BY ... ORDER BY ... frame) FROM source` |
| | `RowNumber`, `Rank`, `DenseRank`, `PercentRank`, `CumeDist`, `Ntile(buckets)` | `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `PERCENT_RANK()`, `CUME_DIST()`, `NTILE(n)` |
| | `Lag` / `Lead(value, offset, default)`, `FirstValue(value)`, `LastValue(value)` | `LAG(value, offset[, default])`, `LEAD(...)`, `FIRST_VALUE`, `LAST_VALUE` |
| `PostgreSqlWindow<TSource>` | `Rows`: the rows of the frame, which LINQ's `Count`, `LongCount`, `Sum`, `Average`, `Min`, `Max`, `Any` and `All` aggregate (after `Where`, as `FILTER (WHERE ...)`, and `Select`) | `COUNT(*) FILTER (WHERE ...) OVER (...)`, ... |
| `PostgreSqlFrame` | `Rows(start, end)`, `Range(decimal? start, decimal? end)`, `Range(TimeSpan? start, TimeSpan? end)`, `RangeMonths(start, end)`; `TextValue` | `ROWS` / `RANGE BETWEEN ... AND ...` |
| `PostgreSqlRecursion` | `WithRecursive(seed, level => step)`, `WithRecursive(seed, level => step, maxDepth)` | `WITH RECURSIVE r AS (seed UNION ALL step) SELECT ... FROM r` |

```csharp
// The two largest orders of each customer, with a running total from the largest. This is
// the tree a provider or a tree rewriter builds with Expression.Call (inside a lambda the
// compiler builds it): called as code, Over throws.
orders
    .Over(
        o => o.CustomerId,
        rows => rows.OrderByDescending(o => o.Total).ThenBy(o => o.Id),
        PostgreSqlFrame.Rows(null, 0), // ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        (o, w) => new Ranked(o.Id, w.RowNumber(), w.Rows.Sum(x => x.Total))
    )
    .Where(r => r.Number <= 2);

// SELECT t1."Id", t1."Number", t1."Running" FROM (SELECT t0."Id", ROW_NUMBER() OVER (PARTITION BY
// t0."CustomerId" ORDER BY t0."Total" DESC, t0."Id" ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
// AS "Number", COALESCE(SUM(t0."Total") OVER (PARTITION BY t0."CustomerId" ORDER BY t0."Total" DESC,
// t0."Id" ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), 0) AS "Running" FROM "Order" AS t0) AS t1
// WHERE t1."Number" <= 2
```

- **Windows.** `Over` yields one result per row of its source, in its order, computed after `WHERE`, joins and `GROUP BY` (a window over the groups of the same `SELECT` may aggregate them) and before `DISTINCT`, `ORDER BY` and paging; a paged, distinct or windowed source is wrapped into a derived table, and so is the result for a filter, a grouping, a join or an aggregate. The partition is one value, a tuple or an object of values (constants dropped), or `null`; the order is `OrderBy` or `Order` of the window's rows followed by `ThenBy`, which sorts as everywhere else in .NET's order (nulls first ascending; `StringComparer.Ordinal` sorts by code point); a `null` frame is PostgreSQL's default (with an order, `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, the current row's peers included). A frame bound is an offset from the current row: negative `PRECEDING`, positive `FOLLOWING`, `0` `CURRENT ROW`, `null` `UNBOUNDED`; a duration is written in seconds (elapsed time, also over a `timestamptz`), `RangeMonths` in calendar months. A `RANGE` with an offset needs exactly one sort key of a matching type (a number, or a date, time, timestamp or interval). The lambdas of the functions and of the aggregates over `Rows` read only their own row (SQL cannot name the current row inside an aggregate), the `default` of `Lag` and `Lead` is read in the current row, and the window may not be read in a lambda or a subquery of the selector. `Lag` and `Lead` take PostgreSQL's three arguments, the default standing for a missing row (a `null` default is PostgreSQL's own and is left out: `LAG(value, offset)`), so with a `null` default they read a nullable value; `FirstValue` and `LastValue` of a frame that may not hold the current row may find no row, where they are `NULL`, so they also have to read a nullable value. The aggregates over `Rows` keep .NET's semantics, as over a group (`Sum` is 0 and `Any` false over no rows); `DISTINCT`, which PostgreSQL has not implemented for window aggregates, is refused.
- **Recursion.** `WithRecursive` is a derived table `(WITH RECURSIVE r AS (seed UNION ALL step) SELECT ... FROM r) AS t`: every row of every level, duplicates included, in no order; a cycle ends where the step's own predicate stops it (a path column, for example). The step's parameter is the level before, which it reads exactly once, in `FROM` or an inner join, never in a subquery, a derived table or on the optional side of an outer join, and the step does not group, as PostgreSQL requires of the recursive term; its columns are matched to the seed's by name, and a constant of the seed is cast to its type (`CAST(0 AS numeric)`), as the seed decides the types of the columns. With `maxDepth` (the seed is level 0), a hidden `"$depth"` column counts the levels and a row deeper than the limit fails the statement with `invalid input syntax for type bigint: "WITH RECURSIVE: a row deeper than the maximum depth of n"`: PostgreSQL has no `RAISE` in SQL, so the step casts that message, read by a scalar subquery the planner does not fold, to `bigint` in the branch of a `CASE` that only such a row reaches. A one-time filter, `WHERE (SELECT COUNT(*) FROM r) > 0`, computes every level before the first row is read, as PostgreSQL computes a recursive query only as far as its reader asks; so a query that reads only some of the rows (`Take`, `Any`, `First`) fails as one reading all of them does, and a walk over cyclic data always ends.

## Mapping

A table is named after the element type and its columns after its public properties with a public getter (indexers and write-only properties are skipped), in declaration order. `[Table]` (including its `Schema`), `[Column]` and `[NotMapped]` from `System.ComponentModel.DataAnnotations.Schema` override the defaults. Identifiers are always double-quoted, so their case is kept. A property whose type is not a scalar (or an array of scalars; a `byte[]` is a `bytea`) is rejected, so navigation properties are not supported.

Nullability follows the CLR: `Nullable<T>`, nullable reference types and references without nullable annotations are nullable columns, and so are a conditional with a nullable branch, a scalar subquery or `Min`/`Max` of a reference type, a column of a set operation that is nullable on either side and every column of a left-joined source. A nullable value read as its value, `Nullable<T>.Value` or a cast `(T)nullable`, is never NULL where the C# evaluates (it would throw), so it compares and joins with `=`, also as a member of a composite key. C# semantics are preserved where SQL differs — equality with a nullable operand uses `IS [NOT] DISTINCT FROM` (a correlation key may still be compared with `=`, which is false for NULL in both languages, and so are the keys of `Join` and `GroupJoin`, which never match null keys; the members of a composite key do), a nullable comparison used as a value becomes `COALESCE(..., FALSE)`, nullable keys sort as `NULLS FIRST` ascending, membership tests used as a value or under `NOT` become `COALESCE(..., FALSE)` (`IN` of a nullable value, `= ANY` of any value, as an array may hold `NULL` elements), a nullable string or number is concatenated as `COALESCE(..., '')`, a lifted `^` of booleans stays NULL, `Contains` of a nullable item against a subquery or an array column also matches a NULL of the sequence (`Contains(null)` is true for a sequence holding a null), a left-joined entity compared with `null` tests a column its table requires (or every column), `Select(...).Distinct().Count()` over nullable group values counts NULL as one of them, and `OfType<T>()` drops the nulls of a nullable sequence. Concatenating a `bool`, an enum or a date or time value is rejected, as PostgreSQL formats them differently from .NET.

## Constants are inline literals

The result is a single string, not a command with a parameter collection. Every constant in the tree — literals, captured variables and in-memory collections — is rendered as a safely escaped inline PostgreSQL literal (for example, `'O''Brien'` for the string `O'Brien`; control and non-space white-space characters become `E''` escapes such as `E'a\u00a0b'`). No bind parameters (`$1`, `@p0`) are produced.

## Native AOT and trimming

The package is marked `IsAotCompatible` and builds without trimming or AOT warnings. Translation reads the public properties of the queried element types to find their columns, so `TextValue` is annotated `[RequiresUnreferencedCode]`: in a trimmed or Native AOT application a property that the code never references is removed, and its column silently disappears from `SELECT`. Keep the properties of every mapped type and then acknowledge the `IL2026` warning at the call site, for example:

```csharp
[DynamicDependency(DynamicallyAccessedMemberTypes.PublicProperties, typeof(Order))]
[UnconditionalSuppressMessage("Trimming", "IL2026", Justification = "Order properties are preserved.")]
static string Sql(IQueryable<Order> orders)
{
    return new PostgreSqlQuery(orders.Expression).TextValue;
}
```
